## 1. 개선 방향과 우선순위

우선 추가할 내용은 **가입 전 체험, 기존 기능을 연결하는 사용 흐름, 장애 상황에서도 결과를 확인할 수 있는 기능**이다.

현재 포트폴리오는 인증·피드·채팅·통화·계좌·관리 기능을 폭넓게 설명한다. 다음 단계에서는 사용자가 서비스를 이해하고 다시 찾아올 이유를 만들면서, 구현한 기술의 신뢰성을 검증할 수 있도록 보완하는 것이 효과적이다.

| 우선순위 | 제안 | 기대 효과 |
|---|---|---|
| P0 | 소개·체험 첫 화면 | 가입 전에 서비스 목적과 핵심 이용 흐름을 이해 |
| P0 | 가입·인증·계정 복구와 기기 관리 | 인증 과정의 혼란 감소, 사용자 계정 통제 강화 |
| P0 | 채팅 중복 방지·재접속 복구 | 재전송·장애 상황에서도 일관된 메시지 처리 |
| P1 | 이어서 하기 홈과 대화→개인 To-do 연결 | 피드·채팅·할 일 사이의 연속성 및 재방문 이유 확보 |
| P1 | 권한을 지키는 검색 | 쌓인 기록을 빠르게 찾으면서 공개 범위 유지 |
| P1 | 알림 설정·차단 정책·신고 상태 조회 | 사용자의 통제감과 서비스 정책의 예측 가능성 향상 |
| P1 | 음성통화 예외 상황 처리 | 다중 기기·네트워크 변경 상황의 통화 경험 개선 |
| P1 | 요청·이벤트 운영 추적 | 사용자 신고에서 실패 단계와 원인 파악 |
| P1 | 관리자 행동 이력과 복원 훈련 | 운영 조치 추적 및 실제 장애 복구 능력 확보 |
| P1/P2 | 설계·테스트·성능 증거 공개 | 포트폴리오 평가 목적이면 초기 단계부터 병행 |
| P2 | 계좌 거래 원장과 대사 | 계좌 도메인을 계속 발전시킬 때 거래 정확성 강화 |

P0는 우선 확인할 기반, P1은 핵심 사용성과 운영 완성도, P2는 서비스 방향과 사용량을 확인한 뒤 확장할 항목이다. 실제 구현 순서는 기존 코드와 테스트 상태를 확인한 뒤 조정한다.

## 2. 로그인 전에 이해하고 체험할 수 있는 첫 화면

### 필요한 이유

조사 당시 첫 진입은 로그인 화면으로 이어졌다. 처음 방문한 사람이 무엇을 할 수 있는 서비스인지 이해하는 과정이 필요하다.

### 추가할 내용

- 서비스 목적을 한 문장으로 설명한다.
- 피드·채팅·개인 할 일의 대표 화면과 이용 흐름을 보여준다.
- `서비스 시작`, `체험하기`, `개발 포트폴리오` 진입을 구분한다.
- 현재의 `Portfolio PPT 보기`는 실제 연결 자료에 맞춰 `프로젝트 소개·PDF` 등으로 변경한다.
- 가상의 게시글·채팅·할 일을 이용한 읽기 전용 체험을 제공한다.
- 체험 데이터는 실제 이용자 데이터와 분리하고 체험임을 명시한다.

### 초기 구현 범위

소개 페이지와 가상 데이터 기반의 읽기 전용 데모부터 시작한다. 가입이나 실제 회원 정보 입력 없이 핵심 화면을 둘러볼 수 있으면 된다.

### 완료 기준

처음 온 사람이 가입하지 않고도 서비스의 목적을 이해하고, 대표 사용 흐름을 한 번 따라갈 수 있다.

## 3. 가입부터 계정 복구까지 이어지는 내 계정 관리

### 필요한 이유

공개 화면에는 이메일 인증, 이메일 기반 찾기, 전화번호·생년월일 기반 찾기가 있다. 이 과정을 사용자 관점에서 일관되게 연결하고, 가입 이후에도 계정을 직접 통제할 수 있게 하면 좋다.

### 추가·개선할 내용

- 전화번호·생년월일의 필요성과 수집 목적을 정리한다. 핵심 이용에 필요하지 않다면 선택 입력 또는 추후 입력을 검토한다.
- 약관과 개인정보 안내를 가입 화면에서 쉽게 찾을 수 있게 한다.
- 인증의 현재 단계, 남은 시간, 재발송 가능 시점, 실패 후 복귀 방법을 표시한다.
- 인증 실패나 화면 이동 후에도 필요한 입력 상태를 보존한다.
- 내 로그인 기기를 조회하고 특정 기기 또는 전체 기기를 로그아웃하는 화면을 제공한다.
- 이메일·비밀번호 변경에는 재인증을 연결한다.
- 계정 복구 토큰의 일회성·만료와 발송·검증 요청 횟수 제한을 점검한다.
- 계정 존재 여부를 불필요하게 드러내지 않는 복구 응답을 검토한다.

공개 로그인 코드에는 비밀번호 입력의 일부 문자를 제거하는 처리가 있었다. 가입·변경·로그인 규칙을 통일하고, 입력을 조용히 바꾸지 않도록 개선하는 것을 권한다.

### 완료 기준

- 사용자가 인증 상태와 다음 행동을 이해할 수 있다.
- 인증 재시도와 화면 복귀에서 입력을 불필요하게 잃지 않는다.
- 계정 복구와 기기 로그아웃의 결과가 실제 접근 권한에 반영된다.
- 권한 회수 정책이 REST 요청과 기존 실시간 연결에 어떻게 적용되는지 명확하다.

참고: [OWASP 계정 복구 지침](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html), [OWASP 인증 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)

## 4. 피드·채팅·To-do를 연결하는 이어서 하기

### 필요한 이유

개별 기능 사이에 연속성을 만들면 사용자가 다시 방문할 이유가 생긴다. 추천 흐름은 다음과 같다.

> 게시글에서 이야기 시작 → 채팅으로 구체화 → 내 할 일로 저장 → 알림을 통해 다시 확인

### 추가할 내용

- 게시글과 메시지에 `내 할 일로 저장` 동작을 추가한다.
- 제목·메모·마감일과 원문 링크를 지정할 수 있게 한다.
- 원문 전체를 자동 복사하기보다 저장할 내용을 사용자가 선택하게 한다.
- 원문 접근에는 기존 공개 범위와 참여 권한을 유지한다.
- 홈에 마지막 대화, 미완료 할 일, 내가 쓴 글의 새 답글을 모은다.
- 재방문자가 한 번의 선택으로 이전 활동에 복귀하게 한다.

개인 To-do와 공동 과제는 구분한다. 개인 할 일을 다른 사람에게 자동 노출하지 않으며, 향후 공동 공간을 추가할 때도 공유 동작과 권한을 별도로 설계한다.

### 완료 기준

대화에서 할 일을 만들고, 나중에 그 할 일에서 원래 대화로 돌아갈 수 있다. 원문 권한이 사라졌을 때도 링크 접근 정책을 지키며 개인 To-do가 자동 공유되지 않는다.

## 5. 공개 범위와 소유권을 지키는 검색

### 필요한 이유

게시글·컬렉션·다이어리·채팅이 쌓이면 과거 내용을 찾는 기능이 중요해진다. 이 서비스에서는 검색 정확도와 함께 검색 권한을 관리해야 한다.

### 추가할 내용

- 콘텐츠 종류, 작성자, 기간, 채팅방 기준으로 검색한다.
- 검색 결과에서 원문 메시지나 댓글의 위치로 이동한다.
- 원문을 볼 수 없는 사람에게 제목·미리보기·첨부파일명·검색 결과 수로 내용이 드러나지 않게 한다.
- 방 탈퇴, 차단, 삭제, 공개 범위 변경을 검색 결과에 반영한다.
- 검색 인덱스나 캐시가 늦게 갱신돼도 응답 시점의 접근 권한을 지킨다.

### 초기 구현 범위

기존 데이터베이스를 활용해 검색 대상을 좁혀 시작한다. 데이터량과 검색 품질을 측정한 뒤 별도 검색 엔진 도입을 판단한다.

### 완료 기준

사용자는 접근 가능한 과거 기록을 찾을 수 있고, 접근 권한이 사라진 콘텐츠는 검색 미리보기에서도 제외된다.

## 6. 알림 설정·차단 정책·신고 진행 상태

### 필요한 이유

SSE 알림은 이미 포트폴리오에서 소개한다. 다음 단계는 알림을 얼마나 받을지, 누구와 연결될지를 사용자가 조절하는 경험이다.

### 추가할 내용

- 댓글·답글·채팅·팔로우·할 일 알림을 종류별로 설정한다.
- 채팅방별 음소거와 방해금지 시간을 제공한다.
- 같은 사건의 알림을 묶고 중복 표시를 방지한다.
- 여러 탭과 기기의 읽음 상태를 맞춘다.
- 알림을 누르면 해당 메시지·댓글 위치로 이동한다.
- 원문이 삭제되었거나 접근할 수 없으면 상태를 설명한다.
- 차단이 피드·검색·새 메시지·통화·기존 공동 채팅방에 각각 어떻게 적용되는지 안내한다.
- 신고·상소의 접수·검토·결과 상태와 본인 이력을 조회할 수 있게 한다.

### 완료 기준

이용자가 알림량을 조절하고 차단의 효과를 예측할 수 있다. 알림에서 원문으로 정확히 이동하며, 자신의 신고·상소 처리 상태를 확인할 수 있다.

## 7. 채팅 재전송·재접속 복구와 명확한 전송 상태

### 필요한 이유

문서에는 outbox·재시도·dead letter가 있다. 이 구성에 더해 같은 요청이 여러 번 도착했을 때의 결과와, 연결이 끊긴 뒤 복구되는 과정을 명확히 검증하면 좋다.

### 추가·점검할 내용

- 메시지를 처음 보낼 때 고유 ID를 만든다.
- 전송 실패 후 재시도할 때도 같은 ID를 사용한다.
- 서버와 소비자에서 같은 메시지·이벤트의 중복 저장과 중복 알림을 방지한다.
- 중복 처리 확인과 업무 데이터 변경의 트랜잭션 경계를 점검한다.
- 화면에 `전송 중`, `저장 완료`, `읽음`, `실패`의 의미를 구분한다.
- 실제 서버 저장을 확인한 뒤 완료로 표시한다.
- 재접속 시 마지막 수신 위치 이후의 메시지를 조회해 누락을 복구한다.
- 방별 서버 순서와 중복 제거 규칙을 문서화한다.

Kafka 전달 보장과 외부 데이터베이스의 반영 결과는 함께 설계해야 한다. 메시징 도구의 설정만으로 모든 업무 결과가 한 번만 반영된다고 가정하지 않는다.

### 완료 기준

- 같은 메시지를 세 번 재전송해도 최종 메시지는 한 개다.
- DB 저장 직후 프로세스가 종료돼도 복구 후 누락이나 중복 표시가 없다.
- Kafka 일시 중단 후 재처리에서도 논리적인 알림이 중복 생성되지 않는다.
- 브라우저 재접속 후 메시지가 서비스가 정한 순서대로 보인다.

참고: [Apache Kafka 메시지 전달 보장](https://kafka.apache.org/41/design/design/#message-delivery-semantics)

## 8. 음성통화의 예외 상황과 사용자 안내

### 필요한 이유

Redis 기반 통화 상태 관리는 이미 설명되어 있다. 다음은 다중 기기와 모바일 네트워크 환경에서의 예외 처리다.

### 추가·점검할 내용

- 여러 기기에 로그인한 사람이 동시에 통화를 수락하는 경우를 처리한다.
- 한 기기가 수락하면 나머지 기기의 벨을 멈춘다.
- 모바일 백그라운드 진입과 복귀를 처리한다.
- Wi-Fi와 모바일 네트워크 전환 시 복구 동작을 정의한다.
- 이전 통화의 늦은 종료 신호가 새 통화를 종료하지 않게 한다.
- `마이크 권한 필요`, `상대 연결 대기`, `연결 복구 중`, `연결 실패`를 구분해 안내한다.
- 복구할 수 없는 상황의 종료 시간과 기준을 정한다.

### 완료 기준

끊긴 통화가 사용자를 계속 통화 중으로 남겨두지 않는다. 여러 기기의 수락·종료 상태가 일치하고, 사용자가 연결 실패 원인과 다음 행동을 이해할 수 있다.

## 9. 사용자 신고 한 건을 끝까지 추적하는 운영 기능

### 필요한 이유

시스템 자원·장애·outbox 현황에 더해, 사용자가 겪은 문제를 처리 단계별로 추적할 수 있어야 한다.

### 추가할 내용

- 메시지 저장·전달 소요 시간을 측정한다.
- 가장 오래 대기 중인 outbox 이벤트와 Kafka 처리 지연을 확인한다.
- 통화 연결 성공률과 이메일 인증 실패율을 확인한다.
- 요청 ID와 이벤트 ID로 관련 로그를 연결한다.
- 로그·추적에 비밀번호·토큰·불필요한 메시지 본문이 기록되지 않게 한다.
- dead letter의 실패 원인, 다음 재시도, 재처리 가능 여부를 표시한다.
- 수동 재처리에도 중복 방지와 실행 기록을 적용한다.

운영자는 “메시지가 안 왔다”는 신고에서 접수·저장·발행·소비·전달 중 어느 단계가 지연됐는지 찾을 수 있어야 한다. 기존 관리자 화면과 지표를 확장하는 방식으로 시작할 수 있다.

### 완료 기준

운영자가 사용자 신고 한 건에서 실패 단계를 찾고, 재처리 여부와 최종 결과까지 확인할 수 있다.

참고: [OpenTelemetry 로그·지표·추적 체계](https://opentelemetry.io/docs/concepts/signals/)

## 10. 관리자 행동 이력과 실제 복원 절차

### 필요한 이유

GitHub 변경 내역과 실제 운영 조치의 기록은 목적이 다르다. 누가 어떤 조치를 했는지 남기고, 백업에서 서비스를 복원할 수 있는지도 확인해야 한다.

### 추가할 내용

- 제재 변경, 상소 처리, 파일 삭제, 통화 강제 종료, 이벤트 재처리에 대한 행동 이력을 남긴다.
- 실행자·대상·시각·사유·결과를 기록한다.
- 변경 전후 값은 필요한 범위로 제한한다.
- 비밀번호·토큰·불필요한 본문은 기록에서 제외한다.
- 격리된 환경에서 DB와 S3 객체·메타데이터를 복원하는 절차를 만든다.
- 복원 후 게시글 이미지·메시지·권한 관계가 정상인지 대조한다.
- 복구 소요 시간과 복구 가능한 데이터 시점을 기록한다.

### 완료 기준

중요한 관리자 조치의 이유를 추적할 수 있고, 백업에서 서비스를 복구하는 절차를 재현할 수 있다. 백업 파일의 존재뿐 아니라 복원된 데이터의 일관성도 확인한다.

## 11. 계좌 기능을 유지한다면 거래 원장과 대사

### 필요한 이유

계좌 영역을 계속 발전시킬 계획이라면 거래의 정확성과 추적 가능성을 강화할 가치가 있다.

### 추가·점검할 내용

- 잔액을 바꾸는 거래에 고유 ID, 원인, 상태를 기록한다.
- 자동이체가 중복 실행돼도 한 번만 반영되게 한다.
- 취소 거래를 원래 기록과 연결된 반대 거래로 남긴다.
- 동시 출금과 잔액 불변식을 검증한다.
- 이자 계산의 소수점·반올림 규칙을 명시한다.
- 만기 경계 시각과 자동이체 실패 후 재시도를 검증한다.
- 거래 기록의 합계와 잔액이 일치하는지 대사한다.
- 서비스 소개에서 모의 계좌인지 실제 금융기관과 연결되는 기능인지 명확히 표시한다.

### 완료 기준

중복 실행과 동시 요청 이후에도 거래 기록으로 잔액을 설명할 수 있다.

## 12. 설계의 효과를 확인할 수 있는 포트폴리오 자료

### 필요한 이유

현재 자료에는 구현 범위와 설계 설명이 있다. 선택 이유와 검증 결과를 더하면 평가자가 프로젝트의 판단 과정과 완성도를 이해하기 쉬워진다.

### 추가할 내용

- outbox를 선택한 이유와 검토한 대안을 설명한다.
- 재시도 중복 방지, 브라우저별 토큰 교체, 개인 To-do의 권한 경계를 실제 사례로 설명한다.
- 짧은 시연 영상과 핵심 화면을 제공한다.
- 도메인 관계도와 통화·메시지 상태 전이도를 추가한다.
- 성능 측정에는 실행 환경·데이터량·동시 접속 수·측정 방법을 함께 적는다.
- 평균뿐 아니라 느린 요청의 분포와 개선 전후를 제시한다.
- 테스트 개수와 함께 어떤 실패 상황을 검증했는지 설명한다.
- 문서의 기술 버전을 실제 배포 버전과 맞춰 유지한다.
- 지원되는 릴리스로 갱신하는 계획을 관리하고 인증·업로드·실시간 통신의 회귀 검증을 병행한다.

### 완료 기준

제3자가 선택 이유를 이해하고, 제시된 테스트나 측정을 같은 조건으로 재현할 수 있다.

참고: [Spring Boot 지원 정책](https://github.com/spring-projects/spring-boot/wiki/Supported-Versions)

## 13. 권장 구현 순서

소스코드와 기존 테스트를 확인하지 않은 상태이므로 소요 기간을 단정하지 않는다. 각 단계의 완료 조건을 기준으로 진행한다.

| 순서 | 묶어서 진행할 작업 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| 1 | 소개·체험, 가입·계정 복구 정리 | 처음 온 사람이 서비스를 이해하고 계정을 관리할 수 있음 |
| 2 | 채팅 중복 방지·재접속, 권한 변경 검증 | 끊김·재전송·방 탈퇴 후에도 데이터와 접근 정책이 일관됨 |
| 3 | 이어서 하기, 대화→To-do, 검색·알림 설정 | 기존 기능 사이를 오가며 다시 이용할 이유가 생김 |
| 4 | 운영 추적, 관리자 이력, 복원 훈련 | 실패 원인을 찾고 처리·복구 결과를 확인할 수 있음 |
| 5 | 측정·시연 자료, 사용량에 따른 확장 | 실제 사용과 검증 결과를 근거로 다음 기능을 선택할 수 있음 |

계좌 원장·대사는 계좌 도메인을 유지·확장할 계획에 맞춰 병행한다. 포트폴리오가 주목적이면 시연과 실패 복구 증거를 1~2단계부터 함께 준비한다.

## 14. 목적에 따른 측정 기준

### 포트폴리오 평가가 주목적인 경우

- 가입 없이 핵심 기능을 이해하거나 시연을 볼 수 있는가.
- 주요 설계의 선택 이유와 제약을 설명할 수 있는가.
- 실패 복구·권한·중복 방지 테스트를 재현할 수 있는가.
- 성능 수치의 측정 조건이 명시되어 있는가.

### 실제 이용자 확보가 주목적인 경우

- 체험에서 가입과 첫 활동까지 얼마나 이어지는가.
- 재방문자가 이전 대화·기록·할 일로 복귀하는가.
- 대화에서 만든 할 일이 실제로 확인·완료되는가.
- 검색으로 필요한 기록을 찾는가.
- 인증·채팅·통화 실패로 이용 흐름이 끊기는 지점은 어디인가.

실제 측정 전에는 목표 수치나 개선 효과를 성과로 제시하지 않는다. 이벤트 수집은 필요한 행동 중심으로 설계하고 콘텐츠 본문·인증정보를 분석 데이터에 포함하지 않는다.
